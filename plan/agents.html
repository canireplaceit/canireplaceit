The API

One route for everything that has a page. Every object carries two links.

The rule the whole surface follows: if it has a URL on the site, it has a route here, and the vocabulary matches the domain types in packages/core/src/content.ts rather than inventing a second naming scheme.

Rate limiting

Two findings while wiring this up, both of which would have bitten silently.

  • Version. elysia-rate-limit@5.x requires elysia 2.0, and this project is on 1.4.29, which is still the latest dist-tag. Pinned to 4.6.3, the last release on the 1.x peer range. Upgrading elysia under a 1,700-line index.ts to gain a rate limiter would have been the wrong trade.
  • The default generator would have made one bucket for the whole internet. It reads server.requestIP(), which behind your nginx is the docker bridge gateway for every caller. It now reads x-forwarded-for, which is safe here specifically because nginx/canireplaceit.conf sets X-Forwarded-For $remote_addr, an overwrite rather than an append, so a client cannot spoof it.

The limiter is scoping: "scoped" on a sub-instance, so the vote, sponsor and Stripe routes keep their own rules. Verified by firing 66 requests and watching it turn over to 429 at the right count, then confirming a different forwarded address gets its own bucket.

Two things make the limit cheap to enforce. The pages are served by a separate nginx container from prerendered files, so hammering the API cannot take the site down, only the API. And every v1 GET carries Cache-Control: public, max-age=300, with an hour on the dump, so a polite caller skips most of its requests.

The skill

One file on disk, three URLs, and a test that stops the digest going stale.

URLFor
/skill.mdA person pasting a link, and anything that just wants to read it
/.well-known/agent-skills/index.jsonThe agent-skills 0.2.0 discovery manifest, with a sha256 digest
/.well-known/agent-skills/canireplaceit/SKILL.mdWhat npx skills add fetches

The file lives at apps/frontend/public/agent-skills/canireplaceit/SKILL.md and nginx serves it under both paths. It is not stored in a dot-prefixed directory because a bundler copying public/ cannot be relied on to carry one, and this way the question never comes up. Content type is text/markdown; charset=utf-8 on both, verified against real nginx in a container.

The skill is a map, not a copy of the data. It teaches the vocabulary, the ranking rules and the routes, then sends the agent to the API. A skill that embedded facts would go stale in the user's ~/.claude folder within a week of a price sweep.

Still to do by hand: the git marketplace repo. Claude Code installs from a repo with .claude-plugin/marketplace.json, not from a URL, so that half needs a second repo and is the one piece of this that is an announcement rather than a commit. The HTTP discovery path above already works for npx skills add and for anything crawling you.

What the skill tells an agent to do

The ranking rules are the interesting part, because they encode judgements the raw data does not: drop anything archived, prefer open_core: "none" over "minor" over "major", match effort to what the person can actually run, mention a last_push older than a year, and when the verdict is not-yet, say so instead of recommending something weak. Then link the url of everything named.

Structured data

Three additions, one refusal.

  • FAQPage on every product page. The one type both Google and the answer engines lift wholesale. Four questions, all built from the record: is there an open source alternative, can you self-host a replacement, how much does it cost, what do you lose by leaving. The cost answer carries the check date and the vendor URL it was read from, which is the part nobody else in this space can publish.
  • Offer on the paid product. Real price, real currency, linking the pricing page it came from.
  • WebSite with a SearchAction on the home page, page one only, pointing at the search API.
  • No offers on projects. seo.ts already carried an explicit decision against this, with a sound reason: an offer only earns a rich result alongside a rating, and inventing a rating is how a site earns a manual action. I left that decision alone and wrote down why the product differs. The product's price is an event with a receipt. A project has no price to state.

A test asserts no JSON-LD block ever contains the string undefined, NaN or "null", across three products in both languages. One absent field is all it takes to publish "checked on undefined".

Feed and IndexNow

/feed.xml is Atom, the 50 most recently re-verified prices. A feed of new products would need a created date the catalogue does not keep, and deriving one from git would be a date about a file rather than about a product. pricing.checkedOn is a real event: a human read a vendor page and wrote down what it said. That is the thing worth subscribing to, and it is the thing nobody else publishes.

IndexNow fires after a successful deploy and never fails one. It submits the index pages every time, plus the specific product pages whose data files changed in that release, worked out with git diff and degrading to index pages only when the checkout has no history. Submitting the whole sitemap every deploy is how a site gets its submissions ignored. It is inert until INDEXNOW_ENABLED is set, so nothing goes out before you want it to. The key sits at /indexnow-key.txt, which is public by design.

Bing matters here more than its search share suggests, because Bing's index is what Copilot answers from.

What is left

Nothing, other than one small thing that belongs to another session.

All three open questions are closed. The data licence is confirmed as CC-BY-4.0, which is what every API response and the skill already state. The git marketplace repo is dropped by decision, and it is the right call: people run different agents, and a Claude-specific install path would have been the one piece of this that served a single vendor. The HTTP discovery endpoint is agent agnostic and already works.

The em dashes are gone. 149 of them plus 5 en dashes, across both language blocks of apps/frontend/src/i18n.ts, rewritten to periods and commas, with no parentheses and no hyphen substitutes. 312 tests still pass and every placeholder was counted before and after to prove none were eaten.

One regression, caught and closed. build-og-pages.ts splits the 404 string on its dash to get two lines for the card, so removing the dash left one long line and an empty second one. It degraded rather than crashed. I did not fix it myself, since that file was being actively edited in another session, and sent them the exact regex instead. They have applied it and verified that the old wording still splits correctly too, so a revert cannot break it either. The card set is regenerating now and picks up the rewritten copy on submit, glossary, gaps, stats and the 404.

Two dashes were left in place on purpose, in both languages: the feature matrix legend ends with · – not checked. That is not punctuation, it is the literal glyph FeaturesPage.tsx renders for an unchecked feature, and the sentence above it reads "A dash means nobody has checked". Rewriting the legend without changing the glyph would make the legend lie. Changing the glyph is a decision about the matrix's visual vocabulary rather than a copy fix, so it is yours to make.

The Markdown twins

8,814 files, one extra write in a loop that already existed.

Every page now has a .md beside it, so canireplaceit.com/en/alternatives/notion.md returns the page without the HTML. Built in scripts/page-markdown.ts from the same payload the React render reads, never by converting the HTML, since converting would inherit the navigation, the sponsor rails and the cookie banner, which is exactly the boilerplate the twin exists to drop.

The shape follows what retrieval actually rewards. The verdict is the first line, the price and the date it was checked are the second, and the reasoning comes after. Then a table, because a table survives being chopped into a chunk. Then a footer carrying the canonical URL on every single file, so a model that ingests only the Markdown still has the link to cite.

Three decisions worth naming:

  • Twins are not in the sitemap. They are alternate representations of a document, not documents. Listing them would ask a crawler to treat one page as two, which is the duplicate-content problem the rest of that file works hard to avoid. Each page instead carries <link rel="alternate" type="text/markdown">.
  • Pages with nothing to say get no twin. The legal documents, the contact form and the dashboard render copy that lives in the React tree rather than in the payload. A stub saying "see the HTML" would be a file that exists to be disappointing.
  • Index URLs get two files. /en/index.md and /en.md, because "append .md to the URL" and "strip the slash and append .md" are both things a caller will try, and two small files beat a rule with an exception in it.

Verified by running the real prerender to completion, then serving the output through the real nginx config and fetching the twins back at the right content type. Every project link in a generated twin was checked against the pages on disk: 12 of 12 resolve.

A data-loss bug, found late

Reported by another session as a determinism problem. It was worse than that.

The OG session noticed that the three language collections changed size depending on the order the product files were read, and that apps/backend/src/content.ts did not sort its readdir while scripts/prerender.ts did. So the API could report different membership than the page it described. That part was exactly right, and the reproduction matched: sorted gave 68/157/158 for Rust, Go and Python, unsorted gave 70/153/159, reversed gave 74/148/159.

The stated cause was different products disagreeing about a project's language, with the first one read winning. I checked how many projects are cited with more than one distinct language. Zero. None disagree, and none disagree about hasCompose either.

The real cause is sparseness. 64 projects carry a language on some citations and none on others, and collectProjects read only the first citation, so whenever the first product to cite a project happened to omit the field, a language the catalogue already held was thrown away. Ardour is cited eight times and named as C++ in three of them, but the first citation is silent, so Ardour had no language at all.

That distinction decided the fix. It was flagged as a product decision needing disagreement handling of the kind factsVary does for facts. With zero conflicts there is nothing to arbitrate, and filling a gap from a later citation is the same move the function already makes one line above for archived and for effort. Those two fields were simply the ones that never got it.

Both fixed: the API now sorts, and the collector fills language and hasCompose from any citation that has them. The result is stronger than determinism.

They are also all higher, which is the real result here: those 13 extra Rust projects were always written in Rust, and the site was discarding the fact. Sorting alone would have frozen the wrong answer rather than corrected it. Two regression tests in packages/core/src/content.test.ts assert that citation order cannot change the answer.

These numbers are user-visible and they moved. The language and compose collection pages will list more projects than they did, and any generated card printing those counts is stale until it is regenerated. Nothing was invented: every project added was already described as that language somewhere in the catalogue.

Corrections

Things the first draft of this plan got wrong, found by reading the code.

  • effort is managed, docker, ops. Not low, medium, high.
  • verdict is yes, almost, not-yet. Not "partial".
  • 592 products and 3,479 projects, not 527.
  • The worst bug I wrote, caught before it shipped. A Project carries a forge id like github-appflowy-io-appflowy, and I was emitting that as the page link. The real page is /en/tools/appflowy, built by buildProjectSlugs. Every project link in the API would have 404'd, which is the one field the whole thing exists to produce. It now builds the same map the prerenderer builds, with the product slugs passed in so collisions resolve identically, and the pretty slug is the public id. The forge id still resolves, since vote rows carry it. A test recomputes the map the way prerender does and asserts every published slug matches.
  • Feature answers were keyed wrongly. I looked projects up by source.path; the generator keys them by healthKey, which prefixes every forge except GitHub with its hostname. Measured: 3,158 resolved before, 3,234 after. Worse than the 76 misses was the collision it hid, since blender/blender exists both on projects.blender.org and as a GitHub mirror. Caught by a peer session reviewing my message rather than my code, which is the only reason I checked.
  • The glossary terms live in the page, not in the content, so DefinedTerm markup would mean copying fifteen definitions into seo.ts and letting them drift. Skipped for that reason rather than forgotten.
  • data/features.json is about to grow a lot, 3,281 projects today and more coming. So /api/v1/features serves the taxonomy and the per-record answers ride on each record. It is read lazily and tolerates the file being mid-rewrite, because another session regenerates it while the server is running.

What was already good

Most sites chasing this in 2026 are trying to buy what this repo already had.

  • Fully prerendered static HTML. Every AI crawler sees the content on first fetch, with no JS render step. Most React sites fail right here.
  • Sharded sitemap with hreflang and honest lastmod, plus deliberate noindex on thin categories and thin projects, and filter states as query params behind a bare canonical. That last part is what everyone gets wrong.
  • Pagination as a path, translated URL segments per locale, and a tested inverse between building a URL and reading it back.
  • pricing.checkedOn, confidence, PriceSource.url, and a health sweep with lastPush and archived. Verifiable dated facts are exactly what answer engines weight, and this is the differentiator the whole plan is built on.
  • Content in git, validated in CI. The API over it was a serialisation job, not a data project.

Deliberately not built

  • skip Remote MCP server. A second protocol over the same queries. The skill and API already cover Claude Code, Cursor and ChatGPT. Worth revisiting once the search API has real usage.
  • skip llms-full.txt. Superseded by per-page Markdown.
  • skip Blocking training crawlers. robots.txt stays open to both retrieval bots and training bots. A directory wants to be memorised, and blocking training crawlers is how sites quietly vanish from Claude and ChatGPT answers.
  • skip API keys and quotas. Auth kills agent adoption. Add it the day someone actually abuses the limit, not before.
One decision still yours. Everything written here assumes the data is CC-BY-4.0, and that string is now returned by every API response and printed in the skill. If that is not the licence you want, say so now, because it is currently a promise the site is making to every caller.
