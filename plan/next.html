3 · Dead ends

E1

Give the 2069 single-product project pages a reason to existrecommended

Right now such a page repeats what the product page already said and is noindexed for it. Three additions would each make it a page worth reading, all from data already held:

medium
  • "Also written in Go" — sibling projects by language, which is the axis a self-hoster actually browses on.
  • "Others in this category" — the project's peers, ranked by exit quality. A project page currently links out to its forge and back to one product.
  • The spec strip — the same five columns the product page now has, comparing this project against its category peers rather than against one vendor.

If they earn content, the noindex can be revisited per page rather than as a blanket rule.

E2

Nothing links to the theme hubs except the categories indexcheap

The ten hubs I shipped are reachable from one page and the breadcrumb. They should also be in the header's Categories dropdown as the top level, with the categories nested under them — which is what the dropdown's own byGroup already computes and then flattens.

E3

The 404 that isn'tyour call

An unknown URL renders the index with a note and noindex — better than a blank page, and it is what I shipped. But it still answers HTTP 200, because the site is static files behind nginx. A real 404 needs an error_page directive in nginx/canireplaceit.conf pointing at a prerendered 404 document. Ten minutes, and it stops a mistyped URL being indexable in principle.

5 · Workflows — keeping it true without you doing it

W1

Link crawl in CIrecommended · do this one

Ten lines, runs after the build, fails the job on any internal href that does not resolve. It would have caught 8260 broken links the day they appeared instead of months later. Nothing else in the test suite can see this class of fault, because it only exists in the assembled output.

~15 lines in the build workflow
W2

Weekly health sweep already exists — wire its output to a pagecheap

health.yml runs weekly and commits health.json. When it flips a project to archived, that is news: it should open an issue, and it should appear on the graveyard page as "newly archived this month". Right now the fact lands silently in a JSON file.

W3

Re-check the oldest prices on a scheduleneeds a decision

Prices drift and the site is judged on them. A monthly job could take the 20 oldest checkedOn dates and open a PR with the pages to re-read. Deliberately a PR and not an auto-edit: a price is a claim, and the whole model here is that a human merges claims.

W4

Contributions: the repo is the admin panel, but nothing says howworth it

"Suggest a change" links to a file on GitHub. For a non-developer that is a wall. A guided form that produces the JSON and opens the PR would widen who can correct the catalogue — and correction volume is the thing that keeps a directory alive.

6 · CLI & dev-tool pages — the spec

You asked for pages for CLI tools and dev tools, by category: what they do briefly, what they replace if anything. Here is the shape I settled on, and it is generating now.

Why these fit the existing model rather than needing a new one

A default tool is a product with no vendor. awk, ssh, cron cost nothing, have no pricing page, and cannot be "cancelled" — but the question the site asks still applies, just inverted: not "can I stop paying" but "should I replace the default, and what does that cost me?" The answer has the same three shapes the catalogue already uses.

C2

The guard that makes this safe to run unattendedalready built in

The prompt forbids the model naming any replacement, and the seeder rejects output that does anyway. Naming a project that turns out not to exist is the exact failure this pipeline was built around — twelve real projects were once dismissed as fictional, and the fix was to never let prose invent a name. Replacements come only from the verify pass, which checks every one against its forge.

7 · What is running tonight

Two stages, chained, checkpointed, restartable. Everything lands on disk in the repo and nothing is committed automatically — you review in the morning.
StageWhatGate
1Seed 70 product stubs. seed-tools.ts — verdict, why, whatYouLose, both locales.Rejects a bad verdict, a missing locale, over-long prose, or any output that names a replacement. Cached per tool, so a restart costs nothing.
2Research alternatives for each, through the pipeline that produced the existing 6230.Every candidate verified against its forge before promotion; anything unresolvable is skipped rather than guessed.
3Validate + test after each batch.bun run validate and the 285 tests. A data fault halts the run rather than looping — that rule is already in monitor.sh.

In the morning: up to 70 new products, several hundred new verified alternatives, shell-terminal and developer-tooling roughly doubled. Then C3 is worth building, because it will finally have the rows to fill it.

Honest limits: some of these have no credible replacement and will land with an empty alternatives list and a "not-yet" verdict. That is the correct answer for ssh and cron, not a failure — but it means the count in the morning will be lower than 70 × something, and the pages that matter are the twenty or so where a real replacement exists.
